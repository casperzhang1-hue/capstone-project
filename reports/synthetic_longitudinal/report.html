Software-validation example

This run verifies the collection and analysis workflow with labelled synthetic data; it is not evidence of physical device performance.

  • 3 analysed session(s), 3 collection date(s), and 1 device(s).
  • 0 session(s) are flagged for quality review; flags remain visible and are not silently excluded.
  • Physical display geometry is recorded for every session; degree fields may be evaluated where target data support them.
  • 1 matched participant/device/protocol repeatability group(s) are available.
  • 3/3 session(s) identify a calibration-error unit.
  • Input provenance is recorded with SHA-256 digest 9779461a21bc….

Report display units

Sampling is in Hz; rates use percent rather than raw 0–1 proportions.

  • valid_gaze_samples_pct = valid_rate × 100
  • data_loss_pct = data_loss_rate × 100
  • QC-filtered target plots use visual degrees because physical display geometry is available.

Traceability

Raw analysis CSV/JSON files remain unchanged. The report adds explicitly named display tables solely to match its figures and tables.

  • Degree fields stay blank without physical geometry.
  • Thresholds flag review items; they do not delete source samples.

Interpretation boundaries

These statements preserve the limits of the supplied measurements.

  • Percent display fields are deterministic conversions, not recalibrated measurements.
  • Normalised screen-coordinate percentages are display-relative quantities, not visual degrees or pixel distances.
  • Visual-angle conclusions require recorded display dimensions and viewing distance; assumed-FOV delay scores are explicitly labelled approximate.
  • Date-level changes are descriptive unless participants, devices and protocols are genuinely matched.
  • QC exclusions are recorded in exports; this report does not silently impute or delete source values.
